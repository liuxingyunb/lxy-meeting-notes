01 / 快速掌握

这次会议主要在对齐什么

主线目标

AIOS 3.0 已进入可上机验证阶段。团队要把已有的机器人业务流程、工具和 skill 迁移/重建到新环境，让已有能力重新运行，并逐步完成导航、上下电梯、按钮技能等端到端串联。

优先级倾向

先恢复并验证基础能力，优先把导航接起来，再接上下电梯及按钮流程；把 Agent 的每轮调用、工具耗时和结果记录出来。感知打断、APP/运营可视化、抓取等能力仍需排期或确认，不能视为已承诺的近期交付。

核心技术讨论

导航、按键等单项能力可以是工具；多步骤业务流程更适合用总流程 skill 调度多个子 skill/脚本。团队讨论先按 AIOS 提供的 skill 方式推进，后续若时延或性能验证表明必要，再评估插件/原生工具接入。

刘星宇相关安排

会议明确希望星宇多投入 A 点相关工作：配合基础流程接入和上机联调，重点梳理工具及 Agent Trace；推进独立日志/可视化信息，把模型响应时延、工具输入参数与返回、调用耗时等记录下来，再用于问题定位、场景评测和后续小模型优化。具体任务边界及交付日期仍应与负责人确认。

阅读说明：绿色标记为会议中较明确的方向；蓝色为讨论中的方案/设想；红色为整理建议或待核对项。说话人编号不是实名映射依据，只有录音明确点名“星宇/新宇”的安排才归入刘星宇相关事项。
02 / 按谈话顺序

详细谈话整理

00:00–03:30
目标与能力盘点

开场提出 AIOS 3.0 已经启动，当前首先要上机，把之前做过的内容迁移过去并跑起来。团队以导航为典型 case：导航侧可能有公司自研方案和外部团队提供的方案，都会提供点到点导航、地图切换等能力；跨楼层场景尤其依赖地图切换。会议倾向于先看现场效果和接口可用性，再决定使用哪个版本，不把底层实现本身当成业务目标。

感知侧被认为可能已与新版本系统做过对接，提到 VIP/人脸识别以及语音能力。语音输入可以支持，但业务操作也需要文字输入；上下电梯过程中若用户发出语音，系统可能需要中断当前任务，这部分还需要联调确认。另提出 APP 联动：机器人执行任务的关键阶段可能要把状态、图像或文字结果反馈给发起者，但哪些轮次需要反馈、通过什么应用展示，当时尚未定案。

03:30–09:30
电梯、抓取与最终任务

讨论把“上下电梯”视作当前关键闭环：除导航外，还涉及抵达电梯、按钮操作、安全判断、乘梯、跨层定位和离开电梯等环节。此前按钮相关流程/模型能力已有基础，但现在从假手换到真手/灵巧手后，按钮动作、关节对齐和执行效果需要重新调试；讨论过统一先用右手按按钮以简化配置。

录音中出现“约 5000 左右”“11 月 5 日左右”“11 月 30 日”“10 月 30 日前”等识别片段，部分上下文不完整或彼此冲突，不据此推导正式项目日期。业务目标还提到取送物：在导航与电梯闭环之后，增加到目标位置取物/抓握技能。是否纳入当前阶段、交付日期和实际依赖需另行核实。

09:30–13:40
迁移、导航联调及按钮接口

AIOS 3.0 至少应能部署到机器上验证。此前 skill/tool 文件在一次迁移中疑似被误删，团队因此要依据仍保留的 skill 文档和原始输入重建/迁移；会议认为已有文档可作为恢复依据。导航供应方会推送新版本并参与上机联调，现场可把问题反馈给供应方处理。机器人当时因展厅安排，预计次日下午才有调试窗口；本周还要协调双方避免抢占设备。

导航试用的初步反馈是大体可用，但曾有低矮障碍识别问题；“突然不动”没有被充分测试，因此不能说已排除。按钮工具由相关同事提供能力/接口说明，团队负责按 AIOS 3.0 的组织方式接入 skill/code；是否要 MCP 取决于最终接口形态，讨论里没有形成需要自建 MCP 的确定结论。按钮描述整体可能不大改，关键是实体手变化后重做姿态、对齐和动作调参。

13:40–19:30
感知、APP 与交付取舍

感知部分的理解是 VIP 识别组件可能部署在本体之外；语音是另一个能力，尤其要测试任务执行中被用户打断后如何停止/接续。联动状态目前没有实际串测，属于空白项，需要把系统间的中断与恢复机制说清楚。

APP 联动被描述为一个较完整的交互设想：用户发送“去电梯并按下行键”等文字任务，机器人导航到电梯、执行按钮动作，必要时先调整姿态；执行过程中把关键阶段的图像和文字状态返回给用户/运营人员。会议随即指出该功能不在既定规划优先序列中，若只做一次成功的 demo 工作量较小；若要每次稳定成功，则需要大量边界处理。当前倾向先确保优先级更高的基础流程，APP 展示先放后。

已有流程可以先基于旧代码和文档恢复；导航可先行串接，等按钮工具可用再接上下电梯。这样可并行准备 skill/流程，但端到端联调要等待依赖到位。

19:30–24:50
Agent Trace 与小模型目标

会议把 Trace 作为重要诊断基础：每轮用户输入、模型响应、工具调用、工具参数、工具结果、执行时间/响应时间都需要可观察。对长任务，还希望看到 global plan/todo 列表中每项的 pending、in progress、complete 等状态，便于判断计划如何变化、哪一步出错。

提出的模型方向是：当前场景虽然有意外，但业务范围相对限定，长期可以探索把模型压到更小规模（转录里出现“9B”“3B/35B”等多个听感不清的数字，不能当成已定规格）。更小模型可能降低资源成本、利于产品化；前提是沉淀真实任务反馈和可用评测，再进行针对性训练。该方向是会议中的目标设想，不是本次已经确定的模型选型。

24:50–32:20
工具、skill 与插件的区别

团队讨论到 AIOS/OpenCode 一类框架自带工具可能较多，旧版本里有冗余项。业务侧希望能筛选系统提示词/框架默认挂载的工具；若不可由应用团队直接删除，则要向框架提供方提出配置需求，或要求提供不挂载默认工具的环境。

会上给出的概念区分是：单个工具提供一个可调用动作，例如点到点导航；skill 除了动作/脚本说明，还可以写多步骤的使用流程与参数要求。例如“上下楼”总 skill 描述顺序，再调用导航、切图、按钮等子 skill。这样按任务只加载相关说明，避免所有工具说明一直占满上下文。与此同时，skill 方式可能增加读取文档/启动脚本等调用开销；插件或原生函数可能更快，但要开发集成，且当时平台建议先按 skill 方式实现，性能不足时再考虑优化。

关于频率，会上讨论高频能力可考虑常驻/插件化，低频能力按需加载；但现阶段官方/平台指导仍是先采用 skill。总体路线以实际测得的端到端时延为依据，不能仅凭“工具调用多一次”断定瓶颈。

32:20–38:30
Trace 缺口与优先级

有人询问 AIOS 3.0 / AI Matrix 是否已有 Agent Trace 和推理过程展示。会议确认相关可视化接口仍在开发或暂不可用；模型服务本身只能反映模型侧耗时，拿不到 OpenCore 中工具调用的完整耗时。因此短期方案是在运行框架中用 hook/调试日志补齐信息，之后再接正式插件或可视化功能。

性能讨论区分了模型推理时延和工具执行时延：举例称普通问答也可能需要约 6–8 秒；导航相关工具启动/调用也可能要 7–20 秒或十几秒。数字是现场经验估计，应以实际测量为准。建议先把链路白盒化，分别计时模型首 token、模型完整输出、工具调用及整个任务，再决定优化模型推理还是工具。

会议倾向的工作顺序是先把导航及上下电梯流程调通/调稳，再优化模型与工具性能；感知可能靠后。与此同时，Trace/性能观测可以与功能联调并行准备。需要为各工具分别提供耗时分析表，不能只看一个总耗时。

38:30–42:50
抓握计划、部署和显示方式

再次提到可能在某个 10 月 30 日前后提供抓握技能，但与谈话其他时间点相互矛盾，录音自动识别也不够可靠，因此作为待核对项。推理模型若由当前团队解决困难，可向负责 AIOS/模型平台的团队提需求；现场提到正在使用或考虑 DeepSeek V4.1、GM 5.3 等模型，名称、版本、是否本地部署需要看实际配置确认。

APP/可视化还遇到网络边界问题：运营侧 APP 若在外网，如何访问内网机器数据尚不清楚。备选思路是先做一个部署在可访问环境中的简单可视化页面或返回工具，不一定必须是独立 APP；OpenCloud 页面可能已有部分可用能力。这里是方案探讨，尚未确定数据链路和安全策略。

42:50–49:36
刘星宇工作内容与近期步骤

会议提出由已有经验的同事先准备基础工具，并在机器人调试初期帮助星宇把流程和工具串起来；基础流程熟悉后再交接，让星宇参与后续调试。星宇可以先尝试具体工作，遇到问题向熟悉工具的同事请教；AI 辅助开发可以用于实现，但需要先弄清业务要观察什么。

对日志/性能观测的具体要求是：日志单独写入文件，不与 OpenCore 主日志混在一起；记录用户输入、模型/token 相关信息、模型首 token/首响应时间、完整响应时间；每个工具的调用名称、输入参数、返回结果及调用耗时都要能查看。完整模型长文本是否写入可按需决定，关键是能判断工具是否选对、参数是否正确，以及总时延由哪一段造成。工具调用正确性和时延是当前场景最关心的指标。

初步计划是先完成一轮实验/日志能力，会上有人提出“11 月 15 日”作为希望争取的时间点；同时提到次日下午一起调试、有人负责提供/部署环境，需把 ARM 机器 IP、连接方式和部署责任人对齐。会议收尾再次强调：一方面做功能调试，另一方面分析问题并反馈给 AIOS/平台团队。转录末尾的个别句子有明显错字，具体交接动作需回听确认。

03 / 概念与系统关系

从会议内容还原业务链条

用户任务（例如去另一个楼层取物）→ AIOS/Agent 理解目标并选择业务流程 → 总 skill 编排子步骤 → 工具/子 skill 执行导航、切地图、按钮或抓取 → 机器人与导航/感知服务产生状态和结果 → Trace/日志记录输入、决策、工具参数、结果、耗时 → 人复盘并改进流程、模型或工具。

该链条是根据会议讨论的组件关系绘制的解释性归纳，不代表每个接口在当前版本都已连通。

工具是什么

一个边界清晰的动作接口，例如导航到站点、切换地图、执行按键。它负责“做一个动作”，通常需要输入参数并返回结果。

Skill 是什么

给 Agent 使用的技能说明/流程包，可以告诉模型何时调用哪些动作、按什么顺序、需要什么参数和注意事项。一个复杂任务常由总流程 skill 和多个子 skill 组成。

为什么做 Trace

机器人失败时要分辨：模型没有规划对、工具参数错误、工具执行慢/失败、导航定位不稳，还是外部环境异常。没有分段记录，就容易把所有问题都归因于“大模型不聪明”。

速度优化怎么判断

拆开测模型首 token、模型完整响应、每个工具执行和全任务耗时。若工具本身占十几秒，单纯换小模型不一定解决主要瓶颈；须以测量结果决定先优化哪段。

06 / 分歧、风险与待确认

当前不能忽略的依赖

  • 迁移材料有缺失：旧 skill/tool 疑似在迁移时被删除；虽有文档可重建，仍应逐项核对与旧行为一致性。
  • 导航能力尚未充分验证：低矮障碍识别曾有问题；“不会突然停住”因测试时长不足而未证实。
  • 真手动作需要重调：按钮流程不能因为已有旧技能就视为可直接复用，关节对齐、手臂选择和按钮命中率需要实机验证。
  • 系统 Trace 缺口：AIOS 3.0 当前 Trace/可视化接口据会议称尚未具备或仍在开发；临时 hook 日志的改动方式、维护边界要有负责人。
  • 演示成功不等于稳定交付：一次 demo 与重复成功运行所需的异常处理量不同；会议明确提醒做范围与稳定性的取舍。
  • 模型与工具时延都可能是瓶颈：对模型规模的讨论不能替代分段计时；导航工具启动本身也可能耗时较长。
  • 跨网络展示未解决：外网 APP/页面如何获取内网数据，仍是开放问题。
